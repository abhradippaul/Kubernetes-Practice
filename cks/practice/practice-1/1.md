## Task 1 — AppArmor + Least-Privilege Service Account (omni namespace)

### Question

A pod in the `omni` namespace has excessive permissions and exposes the `/usr/share/nginx/html/internal` directory publicly.

**Requirements:**

- Apply the AppArmor profile at `/etc/apparmor.d/frontend` to restrict access.
- Use the service account with minimum privileges (not `default`) from the `omni` namespace.
- Delete all other non-default unused service accounts after recreating the pod.

### Solution

**Step 1 — Load and verify the AppArmor profile:**

```bash
apparmor_parser -q /etc/apparmor.d/frontend
aa-status | grep restricted-frontend
```

**Step 2 — Identify the least-privilege service account:**

`frontend-default` has the fewest permissions. Accounts `fe` and `frontend` have additional roles/rolebindings.

**Step 3 — Recreate the pod with the corrected spec:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  labels:
    run: nginx
  name: frontend-site
  namespace: omni
spec:
  securityContext:
    appArmorProfile:
      type: Localhost
      localhostProfile: restricted-frontend
  serviceAccountName: frontend-default
  containers:
    - image: nginx:alpine
      name: nginx
      volumeMounts:
        - mountPath: /usr/share/nginx/html
          name: test-volume
  volumes:
    - name: test-volume
      hostPath:
        path: /data/pages
        type: Directory
```

**Step 4 — Delete unused service accounts:**

```bash
kubectl -n omni delete sa frontend
kubectl -n omni delete sa fe
```

## Task 2 — Secrets as Mounted Volume (orion namespace)

### Question

A pod in the `orion` namespace uses secrets as environment variables.

**Requirements:**

- Extract the decoded value of `CONNECTOR_PASSWORD` and save it to `/root/CKS/secrets/CONNECTOR_PASSWORD`.
- Remount the secret as a read-only volume at `/mnt/connector/password` instead of using env vars.

### Solution

**Step 1 — Decode and save the secret:**

```bash
kubectl get secret <secret-name> -n orion \
  -o jsonpath='{.data.CONNECTOR_PASSWORD}' | base64 -d \
  > /root/CKS/secrets/CONNECTOR_PASSWORD
```

**Step 2 — Edit the pod to mount the secret as a read-only volume:**

```yaml
volumes:
- name: connector-password
  secret:
    secretName: <secret-name>
containers:
- ...
  volumeMounts:
  - name: connector-password
    mountPath: /mnt/connector/password
    readOnly: true
```

## Task 4 — Seccomp Audit Profile for audit-nginx Pod

### Question

Create a pod named `audit-nginx` in the `default` namespace using `nginx:alpine`.

**Requirements:**

- Use the `audit.json` seccomp profile from `/root/CKS`.
- Move `audit.json` into the profiles directory inside the default seccomp directory first.
- Reference the profile in the pod's security context.

### Solution

**Step 1 — Move the profile to the seccomp profiles directory:**

```bash
mv /root/CKS/audit.json /var/lib/kubelet/seccomp/profiles/audit.json
```

**Step 2 — Create the pod with the seccomp profile:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: audit-nginx
  namespace: default
spec:
  securityContext:
    seccompProfile:
      type: Localhost
      localhostProfile: profiles/audit.json
  containers:
    - name: nginx
      image: nginx:alpine
```

## Task 5 — CIS Benchmark Fixes (kubelet, etcd, control plane)

### Question

Run kube-bench with the `cis-1.10` benchmark (config at `/opt/kube-bench`). Fix all `FAIL` items except `1.2.5`, ignoring policy issues.

**Areas to fix:**

- Kubelet service file and `config.yaml` permissions.
- etcd directory ownership.
- `kube-controller-manager` and `kube-scheduler` with `--profiling=false`.

### Solution

**Step 1 — Run node benchmark:**

```bash
kube-bench --benchmark cis-1.10 --config-dir /opt/kube-bench/cfg run --targets node
```

**Step 2 — Fix kubelet file permissions:**

```bash
chmod 600 /usr/lib/systemd/system/kubelet.service
chmod 600 /var/lib/kubelet/config.yaml
```

**Step 3 — Run master benchmark:**

```bash
kube-bench --benchmark cis-1.10 --config-dir /opt/kube-bench/cfg run --targets master
```

**Step 4 — Fix etcd ownership:**

```bash
sudo chown -R etcd:etcd /var/lib/etcd

# If user/group is missing:
sudo groupadd --system etcd
sudo useradd -s /sbin/nologin --system -g etcd etcd
```

**Step 5 — Disable profiling on controller-manager and scheduler:**

```bash
vi /etc/kubernetes/manifests/kube-controller-manager.yaml
vi /etc/kubernetes/manifests/kube-scheduler.yaml
# Add under spec.containers.command:
# - --profiling=false
```

## Task 6 — Falco — Override Rule with CRITICAL Priority

### Question

Falco alerts `File below a known binary directory opened for writing` are firing from an `httpd:2.4-alpine` pod.

**Requirements:**

- Override the rule in `falco_rules.local.yaml` (do not edit the default rules file).
- Set priority to `CRITICAL`.
- Output format: `File below a known binary directory opened for writing (user_id=%user.uid file_updated=%fd.name command=%proc.cmdline)`
- Log alerts to `/opt/security_incidents/alerts.log`.

### Solution

**Step 1 — Enable file_output in `/etc/falco/falco.yaml`:**

```yaml
file_output:
  enabled: true
  keep_alive: false
  filename: /opt/security_incidents/alerts.log
```

**Step 2 — Add override rule in `/etc/falco/falco_rules.local.yaml`:**

```yaml
- rule: Write below binary dir
  desc: an attempt to write to any file below a set of binary directories
  condition: >
    bin_dir and evt.dir = < and open_write
    and not package_mgmt_procs
    and not exe_running_docker_save
    and not python_running_get_pip
    and not python_running_ms_oms
    and not user_known_write_below_binary_dir_activities
  output: >
    File below a known binary directory opened for writing
    (user_id=%user.uid file_updated=%fd.name command=%proc.cmdline)
  priority: CRITICAL
  tags: [filesystem, mitre_persistence]
```

**Step 3 — Hot-reload Falco:**

```bash
kill -1 $(cat /var/run/falco.pid)
# or:
systemctl restart falco
```

**Expected log format:**

```
<timestamp>: Critical File below a known binary directory opened for writing (user_id=0 file_updated=/bin/sleep command=tar -xmf - -C /bin)
```

## Task 7 — SBOM SPDX — Find curl Container in fruits Deployment

### Question

Deployment `fruits` in namespace `salad` has three containers: `apple`, `banana`, `kiwi`. One has `curl` installed.

**Requirements:**

- Identify which container has curl.
- Generate an SPDX JSON SBOM from the image tarball in `/root/ImageTarballs`.
- Save output to `~/bugged-fruit.spdx` and container name to `~/bugged-container.txt`.

### Solution

**Step 1 — Find the container with curl:**

```bash
kubectl exec -n salad fruits-<hash> -c apple -- apk info | grep curl && echo apple > ~/bugged-container.txt
kubectl exec -n salad fruits-<hash> -c banana -- apk info | grep curl && echo banana > ~/bugged-container.txt
kubectl exec -n salad fruits-<hash> -c kiwi -- apk info | grep curl && echo kiwi > ~/bugged-container.txt
```

**Step 2 — Get the image name:**

```bash
kubectl describe pod fruits-<hash> -n salad
```

**Step 3 — Generate the SPDX JSON:**

```bash
bom generate --image-archive /root/ImageTarballs/<image_name>.tar --format json --output ~/bugged-fruit.spdx
```

## Task 8 — Service Account with Projected Token (automated namespace)

### Question

Create service account `bot-sa` in namespace `automated` with automounting disabled. Apply it to the `sweeper` deployment and mount the token as a projected volume.

**Requirements:**

- Service account must not auto-mount to workloads.
- Set `sweeper` deployment's `serviceAccountName` to `bot-sa`.
- Mount the service account token as a projected volume.
- Do not change any other deployment fields.

### Solution

**Step 1 — Create the service account:**

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: bot-sa
  namespace: automated
automountServiceAccountToken: false
```

**Step 2 — Edit the sweeper deployment to add SA and projected volume:**

```yaml
spec:
  serviceAccountName: bot-sa
  volumes:
  - name: token-vol
    projected:
      sources:
      - serviceAccountToken:
          path: token
          expirationSeconds: 3600
  containers:
  - ...
    volumeMounts:
    - name: token-vol
      mountPath: /var/run/secrets/tokens
```

## Task 10 — Network Policy: product-db to web-app + payments Namespace

### Question

Allow ingress to `web-app` (products namespace) from `product-db` (database namespace) and all traffic from the `payments` namespace.

### Solution

**Step 1 — Gather labels:**

```bash
kubectl get pods -n products --show-labels
kubectl get pods -n database --show-labels
kubectl get ns database --show-labels
kubectl get ns payments --show-labels
```

**Step 2 — Apply the NetworkPolicy:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-traffic-to-products
  namespace: products
spec:
  podSelector:
    matchLabels:
      app: web-app
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: database
          podSelector:
            matchLabels:
              app: database
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: payments
```

## Task 12 — Ingress with TLS: rocket-server (space namespace)

### Question

Create ingress `rocket-ingress` in the `space` namespace to load-balance traffic to `rocket-server` on path `/`.

**Requirements:**

- Hostname: `rocket-server.local`
- TLS using secret `rocket-tls`

### Solution

**Step 1 — Check the service port:**

```bash
kubectl describe deployment rocket-server -n space
```

**Step 2 — Create the Ingress:**

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rocket-ingress
  namespace: space
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - rocket-server.local
      secretName: rocket-tls
  rules:
    - host: rocket-server.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: rocket-server
                port:
                  number: 80
```

**Step 3 — Add ingress IP to /etc/hosts:**

```bash
kubectl get svc -n ingress-nginx
echo "<INGRESS-IP> rocket-server.local" | sudo tee -a /etc/hosts
curl -k https://rocket-server.local
```

## Task 13 — RBAC Fix: martin's Access to dev Namespaces

### Question

Developer `martin` needs fine-grained access across three namespaces.

**Requirements:**

- `dev-a` and `dev-b`: all operations on pods.
- `dev-z`: get and list pods only.
- Current setup is too permissive. Recreate objects with the same names.

### Solution

**Step 1 — Inspect current bindings:**

```bash
kubectl get rolebindings -n dev-a
kubectl get rolebindings -n dev-b
kubectl get rolebindings -n dev-z
kubectl get clusterrolebindings | grep martin
```

**Step 2 — Recreate role in dev-a and dev-b (full pod access):**

```bash
kubectl create role pod-admin --verb='*' --resource=pods -n dev-a
kubectl create rolebinding martin-pod-admin --role=pod-admin --user=martin -n dev-a
# Repeat for dev-b
kubectl create role pod-admin --verb='*' --resource=pods -n dev-b
kubectl create rolebinding martin-pod-admin --role=pod-admin --user=martin -n dev-b
```

**Step 3 — Recreate role in dev-z (read-only):**

```bash
kubectl create role pod-reader --verb=get,list --resource=pods -n dev-z
kubectl create rolebinding martin-pod-reader --role=pod-reader --user=martin -n dev-z
```

## Task 14 — Audit Logging: kube-apiserver Configuration

### Question

Enable auditing on the cluster using `/etc/kubernetes/cluster-policy.yaml`.

**Requirements:**

- Log to `/var/log/cluster-audit.log`, retain 10 days, max 10MB, max 3 files.
- Track:
  - Delete secrets in `kube-system` at `Metadata` level.
  - Deployment changes in `default` at `Request` level.
  - Everything else at `Metadata` level.

### Solution

**Step 1 — Write the audit policy:**

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - "RequestReceived"
rules:
  - level: Metadata
    verbs: ["delete"]
    resources:
      - group: ""
        resources: ["secrets"]
    namespaces: ["kube-system"]
  - level: Request
    verbs: ["create", "update", "patch", "delete"]
    resources:
      - group: "apps"
        resources: ["deployments"]
    namespaces: ["default"]
  - level: Metadata
```

**Step 2 — Add flags to kube-apiserver.yaml:**

```bash
vi /etc/kubernetes/manifests/kube-apiserver.yaml
```

Add under `spec.containers.command`:

```yaml
- --audit-policy-file=/etc/kubernetes/cluster-policy.yaml
- --audit-log-path=/var/log/cluster-audit.log
- --audit-log-maxage=10
- --audit-log-maxbackup=3
- --audit-log-maxsize=10
```

**Step 3 — Add volumes and volumeMounts:**

```yaml
volumes:
  - name: audit-policy
    hostPath:
      path: /etc/kubernetes/cluster-policy.yaml
      type: File
  - name: varlog
    hostPath:
      path: /var/log
      type: Directory

volumeMounts:
  - mountPath: /etc/kubernetes/cluster-policy.yaml
    name: audit-policy
    readOnly: true
  - mountPath: /var/log
    name: varlog
```

## Task 15 — ImagePolicyWebhook: Block :latest Tag

### Question

Integrate the `image-bouncer-webhook` service to reject pods using the `:latest` image tag via `ImagePolicyWebhook`.

**Requirements:**

- Create admission config at `/etc/admission-controllers/admission-configuration.yaml`.
- Use kubeconfig at `/root/CKS/ImagePolicy/admission-kubeconfig.yaml`.
- `defaultAllow: false` to always reject `:latest`.
- Fix the existing `app-0403` pod in `magnum` namespace to use tag `:1.27`.

### Solution

**Step 1 — Create admission configuration:**

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
  - name: ImagePolicyWebhook
    configuration:
      imagePolicy:
        kubeConfigFile: /etc/admission-controllers/admission-kubeconfig.yaml
        allowTTL: 50
        denyTTL: 50
        retryBackoff: 500
        defaultAllow: false
```

**Step 2 — Add flags to kube-apiserver.yaml:**

```yaml
- --admission-control-config-file=/etc/admission-controllers/admission-configuration.yaml
- --enable-admission-plugins=NodeRestriction,ImagePolicyWebhook
```

**Step 3 — Fix the non-compliant pod in magnum:**

```bash
kubectl get pod app-0403 -n magnum -o yaml > app-0403-fix.yaml
# Edit: change image tag from :latest to :1.27
vi app-0403-fix.yaml

kubectl delete pod app-0403 -n magnum
kubectl apply -f app-0403-fix.yaml
```

> **Note:** If kube-apiserver becomes unresponsive, restore the backup:
>
> ```bash
> cp -v /root/backup/kube-apiserver.yaml /etc/kubernetes/manifests
> ```
